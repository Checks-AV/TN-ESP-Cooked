Ticket Rail — Documentation

How the game actually works

A full walkthrough of the architecture: how a ticket becomes a database row, how a physical RFID scan becomes a status update, and how three kinds of ESP32 stations cooperate to validate a dish in real time.

01Overview

Ticket Rail is a physical-digital cooking game in the spirit of Overcooked. Orders ("tickets") spawn on a screen with a random dish and a countdown timer. Real ESP32 microcontrollers, stationed around a physical kitchen, read RFID tags glued to plastic "ingredients." As players carry ingredients between stations and scan them, the server tracks what's been done to each one. When a finished dish is presented at the Counter station and scanned there, the server checks whether every ingredient went through the correct sequence of steps — and the ticket is marked served or failed accordingly.

The interesting design problem is that the game logic lives almost entirely on the server, not in the browser or on the microcontrollers. ESP32s are deliberately kept dumb: they scan a tag, know which station they're bolted to, and POST a small JSON message. All the recipe knowledge, validation, and scoring happens in one place — routes/ticketrail.js and routes/esp32comms.js — which makes the system easy to reason about and easy to test without any hardware at all.

02System architecture

Four kinds of things talk to the Express server, each over plain HTTP (and one over Server-Sent Events for push updates):

Game screen
game.ejs — spawns tickets, shows timers, plays sound/visual feedback. Runs entirely client-side except for two things: registering a new order, and receiving pass/fail results.
⇄
Express server
SQLite-backed. Owns the recipe data, the live order table, and every RFID tag's current status. This is the only place validation logic lives.
⇄
ESP32 stations
General (prep), Counter (submit), Reset (utility). Each just POSTs small JSON payloads — no game logic on the device.
⇄
RFID tags
Passive stickers, one per physical ingredient prop. They don't talk to anything themselves — a station's RFID reader scans them and reports the UID to the server.

The control dashboard (gamesettings.ejs) is a fifth participant, but it only talks to the game screen — never directly to the server — via the browser's own BroadcastChannel API (see Real-time updates for why that matters).

03The three station roles

Every physical ESP32 is registered once and permanently assigned to exactly one station — a row in the station table. The station's name is what determines what kind of message the server will accept from that device. This is enforced on the server, not trusted from the device, so a misconfigured or spoofed ESP32 can't do another station's job.

General

Prep stations. Read a tag, report a preparation_method (Chop, Cook, Boil, etc.) performed on it. The server checks station_preparation_method to confirm that particular station is allowed to do that particular action before updating the tag.

message_type: "action"
Counter

Exactly one of these. Scans the finished dish's ingredient tags and submits the order number. This is the only station allowed to call the order-validation endpoint — every other station gets a 403 if it tries.

POST /api/esp/submit
Reset

A utility station with one job: clear a single tag's status back to Default without touching any order. Useful for un-jamming a tag mid-service without resetting the whole kitchen.

message_type: "reset"
New ESP32s that boot and register without specifying a station_id are automatically assigned to General — so adding a new prep station to the kitchen needs zero manual setup in the admin UI.

04Database model

The schema separates three concerns that are easy to conflate: what a dish requires, what a physical device is, and what has actually happened during a live service.

TablePurpose
foodMenu items — "Fried rice", "Sushi", etc.
ingredientsIngredient types — "Chicken", "Rice", etc. (not tied to any one dish)
food_ingredientsWhich ingredients a dish needs, and how many
preparation_methodThe vocabulary of actions — Chop, Cook, Boil, Fry, Slice, Dice, Toast
food_ingredient_preparationThe ordered sequence of prep steps a given dish's ingredient needs
stationPhysical stations — General, Counter, Reset
station_preparation_methodWhich station is allowed to perform which prep method
ESP32DevicesEvery physical device that has ever registered, by MAC address
ESP32TaggerWhich station a given device is currently assigned to
RFIDTagsWhich physical ingredient prop a tag represents, and its live status chain
OrdersLive tickets — one row per spawned order, with a pending/completed/failed/missed status

Notice there's no table storing "what a completed dish looks like" as a single flag — a dish's requirements are always derived on the fly from food_ingredients joined through food_ingredient_preparation, so editing a recipe in the admin UI takes effect on the very next order with no extra sync step.

05The status chain

Each RFIDTags row has one column, current_status, that stores the entire history of actions performed on that tag since it was last reset — as a single arrow-joined string, not a foreign key to a fixed list of states.

Default → Chop → Cook

Every time a General station reports an action, the server reads the tag's current chain, appends the new step's name, and writes the whole string back. When the Counter station submits an order, the server independently builds the expected chain for each ingredient from food_ingredient_preparation's ordered steps, and does a plain string comparison. This means the ordering of steps matters — chopping then cooking is a different chain from cooking then chopping — which mirrors how the physical game actually plays.

This chain-as-a-string approach was chosen over a normalized "current step index" column specifically because it fails loudly and visibly: if you print a tag's current_status, you can read exactly what happened to it, in order, without joining anything.

06Order lifecycle

Here's the full path a single ticket takes, end to end:

  1. Spawn. The game screen's timer picks a random recipe from the ones loaded via GET /api/recipes, builds a ticket element, and starts its own local countdown.
  2. Register. In the same moment, the game POSTs { order_number, food_id } to /api/orders. This is the only place an Orders row actually gets created — the ticket the player sees is purely a visual representation of that row until this call resolves.
  3. Prep. Players carry the physical ingredient props to General stations and scan them. Each scan is a POST /esp32comms/listen with message_type: "action", which appends to that tag's status chain (see above).
  4. Submit. The finished dish's tags are scanned at the Counter station, which sends POST /api/esp/submit with the order number, its own MAC, and the list of scanned tag UIDs.
  5. Validate. The server looks up the order's recipe, builds the expected chain per ingredient, and compares it against each tag's actual current_status. It also checks for extra tags that don't belong to the recipe, and required tags that are missing from the scan.
  6. Resolve. The order's row is updated to completed or failed. Either way, every tag in the system is reset back to Default, so the next order starts clean.
  7. Push. The result is broadcast over Server-Sent Events to the game screen, which marks the ticket served or failed and animates it off the rail.

There's a parallel path if nothing happens in time: the game screen's own local timer runs out first, and it calls POST /api/esp/missed itself — no ESP32 involved. This only succeeds if the order is still pending, so a submit that arrives a split second before the timeout wins the race safely; the missed-update simply affects zero rows.

07ESP32 message reference

Register (any station, on boot)

POST /esp32comms/register
{
  "device_mac": "AA:BB:CC:DD:EE:01",
  "station_id": 1,          // optional — omit to auto-assign to "General"
  "ip_address": "192.168.1.101"
}

Heartbeat

POST /esp32comms/listen
{ "device_mac": "AA:BB:CC:DD:EE:01", "message_type": "ping", "payload": {} }

Prep action (General station)

POST /esp32comms/listen
{
  "device_mac": "AA:BB:CC:DD:EE:01",
  "message_type": "action",
  "payload": {
    "tag_rfid": "TAG-001",
    "action_name": "Chop"   // or a numeric preparation_method_id — both work
  }
}

Clear a tag (Reset station)

POST /esp32comms/listen
{
  "device_mac": "AA:BB:CC:DD:EE:03",
  "message_type": "reset",
  "payload": { "tag_rfid": "TAG-001" }
}

Submit a finished dish (Counter station)

POST /api/esp/submit
{
  "order_number": "07",              // raw 2-digit string, not "K-07"
  "device_mac": "AA:BB:CC:DD:EE:02",
  "tag_macs": ["TAG-001", "TAG-002"]
}

Every one of these is rejected with a clear error if the sending device isn't registered, has no station assigned, or is the wrong kind of station for that message — a General station can't submit, a Counter station can't perform prep actions, and only the Reset station can send reset messages.

08Real-time updates (SSE)

Order results need to reach the game screen the instant they happen, not on the next poll. This is done with Server-Sent Events, not the browser's BroadcastChannel API — those are two unrelated things that happen to share a name. Node's BroadcastChannel only lets threads inside the same Node process talk to each other; it can never reach an actual browser tab over the network. The game screen opens new EventSource('/api/events'), and the server pushes esp-order-complete events down that connection the moment /api/esp/submit resolves.

The browser's own BroadcastChannel is still used, but only for what it's actually good for: syncing the game tab and the control dashboard tab, which really are two tabs in the same browser. The game screen re-broadcasts anything the dashboard needs to know onto that channel after it receives it over SSE.

The monitor works without any changes to the actual game routes: it's a single piece of middleware (routes/esplisten.js) that intercepts just the /esp32comms/* and /api/esp/* paths, mounted before those routers so it sees the request first.

10Known gotchas

  • Orders.order_number is UNIQUE across the table's entire history, not just among pending rows — a new service must call POST /api/orders/clear before spawning ticket #01 again, or the insert fails.
  • The reset-all-tags step after every submit is global — it doesn't scope to just the tags involved in that one order, so two orders in flight at once will interfere with each other's prep progress.
  • The ingredientstatus table still exists in the schema but nothing reads or writes it anymore — tag state lives entirely in RFIDTags.current_status now.
